# Trajectory Transformer

`Trajectory Transformer` is the older but still central trajectory-level sequence model for RL, introduced in `Offline Reinforcement Learning as One Big Sequence Modeling Problem` (Janner et al., NeurIPS 2021).  
It models `state, action, reward` trajectories as a single token sequence and uses sequence decoding for policy behavior.

---

## Overview

- Paper: `Offline RL as One Big Sequence Modeling Problem` (`arXiv:2106.02039`).
- Core claim: a trajectory can be predicted end-to-end like text, so control is generated by decoding plausible futures.
- It is conceptually close to `Decision Transformer`, but the emphasis is on trajectory decoding rather than return-to-go conditioning.
- Standard ordering is temporal concatenation of discretized tokens:
  - `s_1, a_1, r_1, s_2, a_2, r_2, ..., s_T, a_T, r_T`.

---

## Core mechanism

1. Build an offline dataset of trajectories from demonstrations or replay buffers.
2. Discretize each continuous dimension into tokens (uniform/quantile/binning is common).
3. Train a causal transformer as an autoregressive language model over full trajectory token sequences.
4. At inference, condition on observed history and perform decoding to produce future token sequences.
5. Use beam search / return-scored scoring to select the best future rollout (or use goal-conditioned prompts if set up).

This gives control via trajectory synthesis, not value backups.

---

## Why this is your “next-token prediction” baseline

- Works naturally with your stack if you already tokenize observations and actions.
- Very close to plain causal language-model training.
- The planning layer is in decoding strategy, so it is easy to compare against simple greedy rollout vs beam search variants.

When it gets weak:
- inference latency rises with beam width and horizon,
- discretization becomes a bottleneck in continuous domains,
- it is still data-limited to the offline trajectory manifold.

## Comparison chart

| Method | Objective | Conditioning | Inference | Data need | Main strength | Main weakness |
|---|---|---|---|---|---|---|
| **Trajectory Transformer** | next-token over `s,a,r` sequence | history + optional return/goal prompts | beam search / sampled trajectory decode | moderate to large offline trajectories | unified planning-by-decoding with one model | decode latency and quantization error |
| **Decision Transformer** | next-action prediction conditioned on return-to-go | explicit `R_t` token | autoregressive, usually greedy or low-branch | moderate offline trajectories | simpler deploy path, explicit return control | no built-in trajectory-level search |
| **Behavior Transformer / VQ-BeT** | action code autoregression | state + behavior token stream | token-to-token action output | demonstrations, often compacted action tokens | high-fidelity behavior cloning via tokenizer | less explicit long-range trajectory planning |
| **ACT / ALOHA** | chunk-level action prediction with overlap replanning | action history + vision/robot state | chunk decode + receding-window execution | teleop-heavy robot datasets | smooth execution in real robots | chunk scheduling and runtime integration overhead |
| **Model-based MPC (TD-MPC family)** | latent model + value + planning objective | latent states + reward targets | online planner over latent dynamics | large replay + simulator/data for model | can outperform pure sequence models on long horizons | much more component complexity |
| **Diffusion Policy** | conditional denoising of action chunks | observation + tokenized actions | iterative denoising steps per action chunk | trajectory/action datasets | strong for smooth multi-modal behaviors | slower and less drop-in for pure NTP |
| **Dreamer / actor-critic world-model stack** | latent world model + imagined rollouts | latent state planning | imagination then policy query | large offline/online interaction data | strong long-horizon transfer potential | far from “drop-in next-token” refactor |

## Practical implementation notes

- Keep discretization stable:
  - same token bins in training and deployment,
  - fixed clipping/range contract for each state/action dimension.
- Start with low complexity:
  - small beam widths (e.g., `B=2..4`),
  - short rollout horizon.
- Profile decode latency early; this method can become the bottleneck before model forward pass.
- If reward is sparse:
  - include reward-aware scoring in beam ranker,
  - combine with a quick Q-style reranker if needed.
- Real-robot runtime guardrails:
  - clamp commands,
  - enforce actuation and torque limits,
  - timeout and emergency-stop conditions.

Minimal inference loop:

```text
prompt = tokenize(current_state_history)
candidates = beam_search_transformer(prompt, horizon=H, beam_width=B)
score each candidate rollout with reward/goal heuristic
pick best first action
execute action
append transition and repeat
```

---

## Pros

- Clean baseline for trajectory-level token control.
- Minimal algorithmic surface area compared with actor-critic or world-model stacks.
- Strong alignment with tokenization experiments: representation changes are explicit and testable.
- Direct comparison point for return-conditioned vs return-free trajectory generation.

## Cons

- Decoding can be compute-heavy at longer horizons.
- Quantization error can dominate in fine-grain control tasks.
- OOD recovery remains weak unless rollout scoring is augmented.
- Not model-based in the same way as MPC stacks.

## Summary

`Trajectory Transformer` is the foundational trajectory-level sequence benchmark for tokenized control. It is usually the strongest comparison point for evaluating “does trajectory decoding beat token-by-token action decoding,” at the expense of decode cost and discretization design.
