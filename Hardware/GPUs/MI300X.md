# MI300X

**MI300X** is AMD's CDNA 3 datacenter accelerator: **192GB HBM3, 5.3TB/s peak memory bandwidth, and native FP8 matrix compute**. Launched on December 6, 2023, it competes with NVIDIA's [[H100]] and memory-focused Hopper systems. Its appeal for local LLMs is fitting larger models on fewer GPUs—not a guarantee that AMD software or every inference workload will outperform CUDA.

The **tinybox red 4xMI300X** brings four refurbished accelerators into a **$60,000 system with 768GB GPU memory**. The important catch: custom carrier boards, **no GPU-to-GPU XGMI links**, reduced GPU power limits, and no AMD warranty/support for these GPUs.

**Research checked: November 5, 2026.** The [tiny corp listing][tinybox] showed **out of stock**, with batch-one shipping **planned for Q1 2027**. This is a preorder announcement, not evidence of customer deliveries. Specifications below are published claims; this machine was not benchmarked locally.

For broader home infrastructure and model choices, see [[LLM Under Your Floorboards]]. For other accelerator/build options, see [[LLM Inference Hardware]] and [[H100 Builds]].

## Overview

- **MI300X:** Discrete compute accelerator; no CPU cores integrated into the GPU package.
- **MI300A:** Related CPU/GPU APU; do not confuse its shared-memory architecture with MI300X.
- **Standard packaging:** OAM (Open Accelerator Module), normally installed on a purpose-built server baseboard—not a conventional desktop PCIe graphics card.
- **Software:** AMD ROCm/HIP and compatible frameworks, or the separate [[tinygrad]] AMD runtime.
- **Primary workloads:** LLM inference, training/fine-tuning, and HPC; not a gaming/display card.

Sources: [AMD product specifications][amd] and [MI300 architecture documentation][architecture].

## MI300X Hardware and Architecture

| Property | Standard MI300X specification |
|----------|--------------------------------|
| Architecture | CDNA 3; `gfx942` software target |
| Compute organization | 8 accelerator complex dies (XCDs), 304 active compute units |
| Packaging | 4 I/O dies and 8 HBM3 stacks; 5nm/6nm chiplets |
| GPU memory | 192GB HBM3 with ECC |
| Peak HBM bandwidth | 5.3TB/s |
| Dense FP16/BF16 matrix compute | 1,307.4 TFLOPS |
| Dense FP8 matrix compute | 2,614.9 TFLOPS |
| Vector FP32 compute | 163.4 TFLOPS—not its FP16 matrix throughput |
| Standard board power | Up to 750W |
| Host connection | PCIe 5.0 x16 |
| Normal deployment | Passive OAM with server-provided cooling and 54V power |

The chiplets inside one MI300X cooperate as one accelerator. That internal fabric is different from the **external Infinity Fabric/XGMI connections between separate GPUs**. AMD's documented eight-GPU platform connects each GPU directly to the other seven; the new tinybox does not provide those links.

**Compare like with like:** AMD lists both dense and structured-sparse peaks. NVIDIA's headline H100 **1,979 TFLOPS FP16 / 3,958 TFLOPS FP8** figures include sparsity; its dense values are approximately half. Neither sparsity peaks nor dense peaks directly predict LLM tokens/second.

Sources: [AMD specifications and footnotes][amd], [architecture][architecture], and [NVIDIA H100 specifications][h100].

## What PCIe-Only Changes

**768GB is aggregate capacity, not one transparently shared GPU allocation.** The runtime must shard a model, partition work, or run separate replicas. Every GPU still has its own memory budget.

PCIe 5.0 x16 provides roughly **64GB/s per direction** before protocol overhead; the often-quoted 128GB/s adds both directions. That is a host-link ceiling, not proof of the sustained peer-to-peer bandwidth between every GPU pair.

**Inference implications:**

- **Independent jobs:** Four models/replicas that each fit one GPU avoid frequent cross-GPU communication; a natural use of the capacity.
- **Layer/pipeline splitting:** Can fit a larger model, but transfers and serial dependencies can limit single-user decoding; four GPUs do not imply four times the speed.
- **Tensor parallelism:** Repeated collectives make peer bandwidth, latency, topology, and collective-library support important.
- **MoE models:** Sparse expert activation reduces compute per token, but expert placement and routing can introduce communication. All resident experts still consume weight memory.
- **Training:** Gradient synchronization and activation exchange can expose the missing scale-up fabric more strongly than independent inference jobs.

**Unverified on this exact build:** PCIe switch/root-complex topology, peer-access behavior, host-staged fallbacks, sustained collectives, and model-specific throughput. Obtain a topology report and matching benchmarks rather than assuming standard eight-GPU MI300X results apply.

Source distinction: [AMD's normal topology][architecture] versus [tinybox's explicit lack of XGMI][tinybox]. The workload consequences above are **[INFERENCE]**, not measurements of this system.

## What Models Could Fit?

**Calculated lower bounds, not checkpoint file sizes or tested deployments.** For a model with `P` billion parameters, ideal raw weight storage in decimal GB is `P × bits_per_weight / 8`. Quantization metadata, unquantized tensors, KV cache, activations, workspaces, and allocator overhead require additional memory.

| Model scale / example | BF16/FP16 raw weights | 8-bit raw weights | 4-bit raw weights | Capacity assessment |
|-----------------------|----------------------|-------------------|-------------------|---------------------|
| 70B dense | 140GB | 70GB | 35GB | One MI300X has room beyond BF16 weights; context/batch still matter |
| 405B dense | 810GB | 405GB | 202.5GB | BF16 weights exceed four GPUs' nominal 768GB; quantized weights can fit in aggregate |
| 671B MoE | 1,342GB | 671GB | 335.5GB | 8-bit is a tighter candidate; 4-bit leaves substantially more nominal room |

These are **[INFERENCE] capacity estimates**. An engine must support the architecture, quantization format, AMD kernels, and feasible per-GPU shard sizes before a configuration is deployable. A nominal fit does not guarantee long context or useful speed.

**Host RAM is only 192GB.** It cannot hold a complete 405GB/671GB weight image at once. Loading methods, temporary buffers, memory mapping, storage bandwidth, and conversion workflows matter even when final weights fit GPU memory. RAID 0 offers no drive redundancy: keep model sources and valuable data backed up elsewhere.

## Software and Acceptance Checks

**Two distinct paths:**

1. **Normal AMD stack:** Linux `amdgpu`/KFD plus compatible ROCm, [[PyTorch]], and an AMD-capable inference engine. The [versioned vLLM guide][vllm] lists MI300 (`gfx942`); that is GPU-family support, not certification of this custom tinybox.
2. **tinygrad:** Its [AMD runtime][runtime] supports CDNA 3 and has both an AMD-kernel-driver interface and a separate PCI interface. The latter may unbind the GPU from `amdgpu`; do not treat driver modes as interchangeable with the ROCm stack.

Use the seller's validated image/version combination first. Older general tinybox docs describe different GPUs, PSU sizes, and an Ubuntu image; they do **not** establish the final MI300X image, exact package versions, or management behavior.

Before accepting the machine or comparing it with an H100 build:

- Verify four devices, expected memory, PCIe link widths/speeds, and the actual host/peer topology.
- Exercise HBM and sustained compute; inspect uncorrectable errors, temperature, power, throttling, and management logs.
- Measure GPU-pair transfers and four-GPU collectives using the intended driver/runtime path.
- Load the **exact model revision and quantization** you intend to use; confirm no unexpected CPU offload.
- Measure prefill/time-to-first-token and decode separately at stated prompt lengths, output lengths, concurrency, and power limits.
- Record stability and output quality as well as throughput. No model-specific tokens/second result for this exact four-MI300X configuration was established here.

## Power, Cooling, and Home Installation

- **GPU budget:** Four 500W caps allow **2kW for GPUs alone**, before CPU, memory, drives, fans, conversion losses, and PSU losses. This is not a measured wall-power figure.
- **Connections:** Seller specifies **one 220V circuit or two 110V circuits**. Two sockets on the same circuit do not create extra capacity; have circuit ratings, wiring, plugs, and continuous-load headroom checked.
- **PSUs:** 3.4kW of combined PSU ratings is output capacity, not constant consumption or proof every low-voltage input arrangement is adequate.
- **600W operation:** Seller suggests it may be possible but warns about heat/noise; do not budget around an unvalidated higher-power configuration.
- **Heat:** Nearly all consumed electrical power becomes room heat. The GPU budget alone corresponds to approximately **6,800 BTU/hour** if fully used; full-system room heat is higher.
- **Noise:** The advertised sub-50dB figure lacks distance/load/ambient details. Do not equate it with silence or assume it holds at higher power.

See [[LLM Under Your Floorboards]] for broader electrical, cooling, and local-model planning. A ventilated equipment space is more appropriate than a sealed underfloor cavity.

## When It Makes Sense

**Strong candidate:** An experienced local-AI owner who needs substantial HBM capacity, can tolerate AMD/custom-platform debugging, and can verify the intended model/runtime before committing money.

**Poor match:** Someone needing guaranteed immediate delivery, AMD-backed system support, drop-in CUDA compatibility, or known fast multi-GPU tensor-parallel training.

**Bottom line:** The offer buys unusually large aggregate HBM capacity in a complete system. The trade is refurbished custom hardware, preorder risk, and no XGMI—not a proven replacement for a fully interconnected enterprise accelerator server.
